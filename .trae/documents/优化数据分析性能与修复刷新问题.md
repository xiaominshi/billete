导致“数据分析”卡顿且无法刷新的主要原因在于：

1.  **每次请求都重复计算 (Performance)**：
    *   每次您点击“统计”或切换天数，后端都会调用 `get_kpi_stats`, `get_daily_stats`, `get_top_routes`, `get_airline_stats`, `get_hourly_stats`, `get_customer_stats` **这 6 个函数**。
    *   每个函数都单独执行 SQL 查询（`COUNT(*)`, `GROUP BY`, 正则处理等）。
    *   在 Render 上，这相当于**串行执行 6 次跨洋数据库查询**，加上数据传输，导致响应极慢。

2.  **浏览器缓存 (Stale Data)**：
    *   目前前端请求虽然加了时间戳防缓存 (`/stats?t=...` 用于简略统计)，但在详细统计 `loadDetailedStats` 函数中调用的 `/stats/detailed?days=...` **没有加时间戳**。
    *   这导致浏览器（尤其是 Chrome）可能会缓存上一次的 GET 请求结果，导致您点击后看到的还是旧数据，必须刷新页面才能强制重新请求。

3.  **启动时自动删除 (Data Loss Risk)**：
    *   `database.py` 在最后一行调用了 `delete_old_history(30)`。这意味着每次服务器重启（或 Render 自动休眠唤醒）时，**超过 30 天的历史记录会被无情删除**。
    *   这对于数据分析是非常不利的，因为您可能想看 90 天甚至更久的数据。

---

### 解决方案计划

我们将采取三步走策略：**修复缓存问题** -> **优化查询性能** -> **保护历史数据**。

#### 1. 前端修复 (index.html)
*   **强制刷新**：在 `loadDetailedStats` 的 `fetch` URL 后追加时间戳参数 `&t=` + `new Date().getTime()`，确保每次点击都获取最新数据，解决“必须刷新页面”的问题。
*   **加载状态**：在请求发起时显示“加载中...”提示，防止用户以为没反应而重复点击。

#### 2. 后端性能优化 (database.py)
*   **合并查询**：目前是 6 次独立的 DB 连接和查询。我们将重构为一个 `get_all_stats_aggregated` 函数，在一个数据库连接（Session）内并行或连续执行所有 SQL，减少连接握手开销。
*   **SQL 优化**：简化部分 Python 层面的正则处理，尽量利用 SQL 的能力（尽管 SQLite/Postgres 差异限制了部分高级 SQL，但仍可优化）。

#### 3. 数据保护 (database.py)
*   **移除自动删除**：**删除**文件末尾的 `delete_old_history(30)` 调用。历史数据应该保留，除非用户手动点击“清空”。这样您可以分析长期的业务趋势。

#### 4. (可选) Render 专用优化
*   如果数据量极大，未来可以考虑加 Redis 缓存，但目前上述优化应足以解决“几秒钟”内的卡顿。

**总结**：修复后，点击“统计”将立即发起新请求（不读缓存），且后端处理速度将提升，同时您的历史数据不再会被自动删除了。
