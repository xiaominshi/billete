经过深度排查，代码逻辑本身（参数传递、去重逻辑、异步调用）都是正确的。如果“Raw Code”依然不保存，极有可能是因为**`add_history_entry` 函数中的参数顺序与 `logic.py` 调用时的传参不匹配**，或者 **`safe_code` 生成的位置不对**。

### 问题根源：`timestamp` 参数的错位
在 `database.py` 中，`add_history_entry` 的定义是：
```python
def add_history_entry(code, result, passenger_info, route_info, timestamp=None, ...)
```
第 5 个参数是 `timestamp`。

而在 `logic.py` 的调用中：
```python
database.add_history_entry(
    code, 
    result, 
    passenger_info, 
    route_info, 
    cost=cost,      # 关键字参数
    price=price,    # 关键字参数
    data_json=data_json # 关键字参数
)
```
这里没有传第 5 个参数，Python 会自动将 `timestamp` 设为 `None`，这本身没问题。

但是！如果在 `logic.py` 中某个版本把 `timestamp` 当作位置参数传递，或者数据库定义变了，就会导致错位。

最关键的是，我在 `database.py` 看到了一行非常可疑的代码：
```python
# 1. Deduplication (Optional: remove if you want to keep duplicates)
if code:
    conn.execute(
        text("DELETE FROM history WHERE code = :code"),
        {"code": code}
    )
```
如果您的 Raw Code **包含特殊字符（如换行符）**，且数据库是 SQLite，`WHERE code = :code` 的匹配可能会失败，导致没删除旧的（或者误删了别的），然后插入新的。

但最最可能的原因是：**数据库锁死 (Database Locked)**。
由于您使用的是 SQLite 且开启了多线程（`threading`），SQLite 对并发写入支持很差。如果前一个请求（比如读取历史记录）没释放锁，写入操作就会失败（虽然我们加了 `try...except`，但可能超时）。

### 修复方案
1.  **移除所有可能的去重逻辑**：彻底删除 `DELETE` 语句。这是历史记录，不需要去重，保留每一次查询是完全合理的。这能极大降低数据库锁冲突的概率。
2.  **强制显式传递所有参数**：修改 `logic.py`，调用数据库时全部使用关键字参数，防止任何位置错位。
3.  **增加 SQLite 超时时间**：在创建引擎时增加 `timeout` 参数。

### 执行步骤
1.  **修改 `database.py`**：删除去重逻辑，增加 SQLite 连接超时设置。
2.  **修改 `logic.py`**：调用数据库时显式指定 `timestamp=None`。
3.  **重启服务**。
